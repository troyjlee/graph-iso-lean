# Lean development plan for string isomorphism with group operation costs

Prepared 18 October 2026.

## Objective and completion criteria

Develop a reusable Lean library for string isomorphism under a finite permutation group, including coset-valued answers, the elementary Luks reductions, and explicit costs for group operations. This is the first algorithmic milestone toward formalizing Babai's algorithm.

The milestone is complete when one executable solver, instantiated with a proved backend, returns either an empty answer or a representative and generators describing **all** isomorphisms, and its cost is bounded in a specified operational model. The same reduction proofs must also apply to a backend whose operation costs are supplied as explicit hypotheses. This lets later work improve group algorithms without rebuilding the string-isomorphism theory.

Required deliverables:

1. Semantic definitions and exact correctness theorems for full and windowed string isomorphism.
2. Finite data representations with proved interpretations in mathlib.
3. A group-operation interface with semantic, cost, and output-size contracts.
4. Correctness and cost composition for orbit decomposition, subgroup branching, and restriction to an invariant domain with lifting back to the original group.
5. A terminating solver using those reductions, with a fully verified finite-enumeration backend for small instances.
6. A documented boundary between proved backend costs and assumptions about future efficient backends.

Polynomial-time Schreier–Sims, the bounded-composition-factor theorem for Luks's algorithm, and Babai's local certificates and Split-or-Johnson belong to subsequent milestones. This milestone makes no general polynomial or quasipolynomial running-time claim.

## Mathematical conventions

### Domains and permutation multiplication

Develop the semantic layer over a finite type `Ω` and an alphabet `Σ`. Use `Equiv.Perm Ω` and mathlib subgroups. Only decidable equality on `Σ` is needed for comparing finitely many symbols; executable inputs will use bounded integer symbols.

Fix mathlib's composition convention throughout:

\[
(g h)(u)=g(h(u)),\qquad (g\cdot x)(u)=x(g^{-1}(u)).
\]

Define the elementary matching predicate directly:

\[
\operatorname{Matches}_W(g;x,y)
\iff \forall u\in W,\ x(u)=y(g(u)).
\]

For the full domain, this is equivalent to `g • x = y` for the indicated action. Prove this bridge once. Use the direct predicate in executable checks to avoid constructing inverse permutations unnecessarily.

For a subgroup `G` and a representative `σ`, define

\[
\operatorname{Iso}_W(\sigma G;x,y)
=\{g\in\sigma G:\operatorname{Matches}_W(g;x,y)\}.
\]

Use **left cosets** `σ G = {σ * h | h ∈ G}`. The source literature often uses a right-action convention, so translate formulas before using them. Include noncommuting permutation examples among the first checks.

### Invariant windows and the answer subgroup

Require `W` to be `G`-invariant whenever the answer is represented as a single coset. This hypothesis is part of the input invariant, not an implicit convention. The representative `σ` need not preserve `W`.

Define

\[
\operatorname{Aut}_W(G,x)
=\{h\in G:\forall u\in W,\ x(u)=x(h(u))\}.
\]

Prove that this is a subgroup using invariance of `W`. Then prove the central theorem:

\[
\tau\in\operatorname{Iso}_W(\sigma G;x,y)
\Longrightarrow
\operatorname{Iso}_W(\sigma G;x,y)
=\tau\operatorname{Aut}_W(G,x).
\]

The output subgroup is therefore the source-string automorphism subgroup inside the input group. It must be complete: exhibiting some automorphisms is insufficient.

Normalize a coset input by replacing `y` with `z = y ∘ σ`. Prove

\[
\operatorname{Iso}_W(\sigma G;x,y)
=\sigma\operatorname{Iso}_W(G;x,y\circ\sigma).
\]

Charge for constructing or accessing the transformed target. Retain the coset form at the public interface so reductions can update representatives without repeatedly copying whole strings.

## Representations and interfaces

Keep semantic objects separate from finite data. A mathematical subgroup can occur in specifications without making membership in it a free computational operation.

| Object | Executable representation | Semantic invariant |
|---|---|---|
| Domain | `Fin n` | Exactly `n` positions |
| String | Length-indexed array of `Fin q` | Interprets as `Fin n → Fin q` |
| Permutation | Forward and inverse arrays | Arrays are mutually inverse bijections |
| Permutation group | List or array of represented generators, with optional backend data | Denotes the subgroup generated by their interpreted permutations |
| Window | Finite list without duplicates, plus a membership representation | Represents a subset invariant under the current group |
| Coset | Represented permutation and represented group | Denotes `σ G` |
| Result | `none` or `(representative, generators)` | Empty set or exactly the corresponding solution coset |

Use semantic interpretation functions such as `PermRep.denote` and `GroupRep.denote`; exact names are to be settled in the first implementation phase. Connect generator semantics to `Subgroup.closure`. Prove invariance of a finite window from invariance under the supplied generators, so executable validation does not quantify over all group elements.

Keep proof fields in `Prop` and require the data-producing path to be executable. Classical reasoning is acceptable in proofs; `Classical.choose` must not supply a returned representative, lift, transversal, or generator list.

Track four sizes separately: ambient degree `n`, active window size `m`, generator count `s`, and alphabet encoding width `b`. Also track the size of backend data and intermediate generator lists. A window of size `m` does not make operations on permutations of `Fin n` cost only `O(m)`.

### Backend contracts

Each operation returns finite data and is accompanied by a theorem specifying its meaning, cost bound, and output-size bound. Start with the smallest interface needed by the solver.

| Operation | Required specification | Cost parameters |
|---|---|---|
| Permutation application, composition, inverse, equality | Agreement with interpreted permutations | Degree and representation size |
| Group membership | Boolean is true exactly for membership in the generated subgroup | Degree, generator count, backend size |
| Generated subgroup and generator insertion | Exact subgroup generated by the inputs | Input and output generator counts |
| Orbit and orbit partition | Exact orbit, or disjoint nonempty invariant blocks covering the window | Degree, window size, generators, output size |
| Point stabilizer | Generates `{g ∈ G | g u = u}` | Degree, generators, orbit size |
| Left transversal for a supplied `K ≤ G` | Distinct cosets whose union is `G` | Input sizes and index `[G : K]` |
| Restriction to an invariant domain | Image action, kernel generators, and constructive lifting data | Ambient and restricted degrees, generators, output size |
| Optional generator compression | Same generated subgroup with a proved output bound | Original list size and resulting backend size |

For images, lift the requested representative and subgroup generators; prove each lift maps to the requested element and lies in the original group. Include kernel generators when reconstructing a full preimage subgroup.

Enumerating a transversal may require writing `[G : K]` permutations. Its contract must expose this output dependence. Do not assume a bound polynomial in `n` independent of the index.

Do not include general string stabilizers, arbitrary setwise stabilizers, or unrestricted coset intersection as primitive polynomial-time services. Such operations can conceal the problem being formalized. Obtain the block-system kernel through an explicit induced action or a proved construction instead.

## Cost model

### Operational accounting

Use a small explicit program semantics or a carefully restricted costed computation interface. Its constructors must cover local data operations, branching, bounded iteration, and backend calls. Prove that evaluation returns both the specified result and a trace of charged operations. A result paired with an arbitrary counter is not a cost proof.

A backend event records the operation and actual size parameters of that call. Keep these events rather than only counting calls: two membership calls may operate on very different generator lists. Local work records array access, symbol comparison, copying, iteration, and allocation according to the chosen model.

For an admissible backend cost schedule `B`, use

\[
\operatorname{cost}_B(t)
=\operatorname{localCost}(t)
+\sum_{e\in\operatorname{backendEvents}(t)}B(e).
\]

Prove additivity under sequential composition and monotonicity under increasing backend bounds. A backend substitution theorem should replace each abstract call by its implementation and bound the resulting cost by this expression. Charge a backend call through its implementation or its contracted bound, never both.

### Concrete accounting choices

Adopt a stated model with constant-cost access to an indexed cell and bounded index arithmetic. Charge copying, scanning, and materializing arrays by their lengths; do not assume all persistent-array updates are constant-time. Charge equality of arbitrary encoded symbols by `b`, unless the input contract ensures each symbol fits in one model word.

Permutation composition, inversion, and equality then have linear upper bounds in the degree; evaluation of a stored permutation is one lookup. Validate this for the selected implementation. A list-based reference implementation must instead use the cost of list traversal.

Prove finite inequalities with explicit size parameters first. Derive asymptotic statements only after proving bounds on intermediate representations. Preserve costs for input validation, preprocessing, output construction, and generator compression when those operations are present.

The deliverable is a bound for this explicit semantics. A simulation into a standard machine model and a bit-complexity corollary are separate follow-up obligations; neither follows merely from attaching counters to Lean functions. Mathlib's `Mathlib.Computability.TuringMachine.Computable` supplies relevant machine-time definitions for that later bridge [M5].

## Reductions to formalize

### Sequential processing of invariant windows

Suppose `W₁` and `W₂` are `G`-invariant, and the first call returns

\[
\operatorname{Iso}_{W_1}(\sigma G;x,y)=\tau H.
\]

Prove

\[
\operatorname{Iso}_{W_1\cup W_2}(\sigma G;x,y)
=\operatorname{Iso}_{W_2}(\tau H;x,y).
\]

If the first answer is empty, terminate immediately. Otherwise process the second window inside the **updated** coset. Since `H ≤ G`, the second window is still invariant under `H`. The cost is the first call, the second call when needed, and explicitly counted bookkeeping. No independence assumption between the two restricted actions is needed.

Extend this to a partition into `G`-orbits. Processing every orbit independently in the original group can produce incompatible witnesses; the sequential formulation prevents that mistake.

### Branching over a subgroup

For a supplied `K ≤ G` and a left transversal `R`, prove

\[
\operatorname{Iso}_W(\sigma G;x,y)
=\bigcup_{r\in R}\operatorname{Iso}_W(\sigma r K;x,y).
\]

A decision procedure may stop at the first witness. The required coset-valued procedure must recover every solution. If the nonempty branch answers are `τᵢ Hᵢ`, select one `τ₀` and return `τ₀ H`, where

\[
H=\left\langle\bigcup_i H_i\ \cup\
\{\tau_0^{-1}\tau_i:i\}\right\rangle.
\]

Prove `H = Aut_W(G,x)` using both the exhaustive branch cover and the solution-coset theorem. Generating a subgroup from an arbitrary union of cosets can overapproximate the union; this reconstruction is justified by those two hypotheses. Include nonnormal subgroups in the verification examples.

The cost inequality must include transversal generation, all executed branch calls, representative differences, collection of branch generators, and any compression. Before compression, record the bound

\[
s_{\mathrm{out}}\leq\sum_i s_i+k-1,
\]

where `k` is the number of nonempty branches. An exponential generator list cannot be silently replaced by a short one.

### Restriction and lifting

For a `G`-invariant domain `W`, normalize the target first, then form the action homomorphism

\[
\rho:G\longrightarrow\operatorname{Sym}(W).
\]

Solve the restricted instance in `ρ(G)`. If its answer is `τ′ H′`, compute a lift `τ` and generators for `ρ⁻¹(H′)` using kernel generators and lifts of generators of `H′`. Prove that this reconstructs exactly the original windowed answer, and then restore the outer representative `σ`.

Restrictions can lose faithfulness. Dropping `ker ρ` loses valid automorphisms, even if a representative is lifted correctly. The correctness theorem must cover this case explicitly. Finite reindexing `W ≃ Fin m`, induced generator construction, lift construction, and conversion back to the ambient domain all incur costs.

### Reduction through a block system

As a final integration example, accept a certified nontrivial `G`-invariant partition of the active window. Construct the induced action on its blocks and its kernel `K`; obtain the kernel either through a proved induced-action implementation or the reference backend. Branch over `G/K`, then process the invariant blocks under `K`.

Prove the resulting reduction and cost formula with `[G : K]` left explicit. Finding a useful block system and bounding the induced group are later tasks. This example prepares the interface used by Luks without assuming the structural theorems that make Luks efficient.

## A terminating executable solver

Implement a basic strategy after the reduction lemmas are proved:

1. For an empty window, return the input coset.
2. If the group fixes the window pointwise, check the representative on the window and return the whole input coset or `none`.
3. If the action has several orbits on the window, process them sequentially using updated cosets.
4. Otherwise, choose a point `u` in the transitive window, branch over its stabilizer, and recurse. The window has at least two points in this case.

Prove termination with a lexicographic measure based on

\[
\bigl(|W|,\ |\operatorname{im}(G\to\operatorname{Sym}(W))|\bigr).
\]

Orbit calls have smaller windows. Point-stabilizer branches have strictly smaller image on the current window. These are semantic proof measures; the implementation need not compute group orders to establish termination. Restriction helpers must lead to a decreasing recursive call rather than repeatedly calling the solver on an isomorphic instance of the same measure.

Represent alternative reduction choices by explicit data and proofs of coverage and progress. Keep the default strategy fully executable. Do not pass a solver for the entire current problem as a backend assumption.

Provide an independent exhaustive solver for tiny inputs. Enumerate the generated group by closure under the supplied generators and their inverses, prove the enumeration exhaustive, and filter by `Matches`. Use one witness and differences from it to construct the answer subgroup. This supplies a simple correctness oracle for examples and a proved implementation of the required group operations.

For the reference backend, derive finite cost bounds in `n`, `s`, and `N = |G|`, including the searches used for duplicate detection; then use `N ≤ n!` only as a coarse corollary. Its role is to instantiate the contracts and expose hidden work, not to supply the eventual efficient complexity theorem.

## Implementation phases and acceptance gates

| Phase | Work | Acceptance gate |
|---|---|---|
| 0 | Create the Lean project, apply the exact dependency pins, settle composition and coset conventions | Minimal files compile; executable examples distinguish `g*h` from `h*g` |
| 1 | Definitions, invariant windows, automorphism subgroup, normalization, and solution-coset theorem | Exact set-equality theorems, including empty domains and arbitrary outer representatives |
| 2 | Finite representations and backend specifications | Every operation has a semantic contract and cost/output-size parameters; decoded inputs match specifications |
| 3 | Cost semantics and backend substitution | Composition and monotonicity theorems; no hidden data-producing operations outside the accounting interface |
| 4 | Sequential windows, subgroup branching, and coset reconstruction | Complete answer theorems and cost formulas; nonnormal subgroup cases covered |
| 5 | Restriction, lifting, and block-system integration | Kernel retained; reindexing and lifts proved; degree changes reflected in costs |
| 6 | Default recursive solver and reference backend | Termination, exact output semantics, finite cost bound, and an actual executable instantiation |
| 7 | Integration checks and dependency audit | Clean build, regression examples, theorem assumptions documented, and an explicit list of efficient-backend work remaining |

The initial development sequence should prove the solution-coset theorem and sequential-window theorem before building a broad backend. These proofs establish whether the representation choices are sound. Develop the cost interpreter before implementing the recursive solver so accounting is part of the implementation from the start.

Use phase gates rather than a fixed calendar estimate. Re-estimate after phases 1–3, when representation overhead and the backend proof burden are visible.

## Verification and final theorem audit

Use proof-level examples and exhaustive comparisons on small permutation groups. Include the trivial group, cyclic and dihedral actions, `S₃` or `S₄`, intransitive actions with linked components, nonnormal subgroups, and actions whose restriction has a nontrivial kernel.

Test constant strings, distinct-symbol strings, impossible matches, nonidentity outer representatives, empty windows, and singleton domains. Compare denoted solution sets, not the particular witness or generator ordering. Different implementations can legitimately return different representations of the same coset.

For concrete regression runs, compare the recursive solver against exhaustive enumeration and check that the recorded costs satisfy the proved bounds. In Lean, prove the generic contracts; finite examples supplement those proofs.

The theorem map should record these final targets, with names explicitly treated as proposed:

- `solve_correct`: the denotation of the returned answer equals `Iso_W(σ G; x, y)`.
- `solve_none_iff`: `none` occurs exactly when the solution set is empty.
- `solve_some_group`: a successful answer's generators generate `Aut_W(G,x)`.
- `solve_cost_le`: cost is bounded by the reduction recurrence with every backend call and local operation accounted for.
- `solve_backend_refinement`: any implementation satisfying the backend contracts preserves correctness and instantiates the generic cost bound.
- `solve_reference_correct_and_cost`: a concrete executable implementation satisfies correctness and a finite cost bound without an assumed group oracle.

Inspect `#print axioms` for the principal theorems and check the executable dependency path. No `sorry`, `admit`, custom axioms, or unproved mathematical backend contracts may enter the concrete completion theorem. Keep conditional efficient-backend results explicitly parameterized by their hypotheses. Standard Lean foundational axioms used by mathlib are acceptable; classical existence proofs must not replace executable output construction.

The next milestone can replace enumeration operations with verified orbit algorithms and Schreier–Sims, proving generator-size and polynomial operation bounds. Once those contracts are discharged, the reductions developed here can be reused in the bounded-factor Luks algorithm and later in Babai's recursion.
